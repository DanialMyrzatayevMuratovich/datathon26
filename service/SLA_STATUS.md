## Почему 85% превратились в 77,5%

[Машинный отчёт](reports/api-speed-regression.json) получен без загрузки моделей или кадров:

```bash
uv run python -m service.quality_gate --baseline runs/jury/20261017T2214-5d08 --candidate runs/jury/20261018T0039-5f22 --out service/reports/api-speed-regression.json
```

| Проверка | `2214-5d08` | `0039-5f22` |
|---|---:|---:|
| Полнота real API | 40/40 | 40/40 |
| Верные вердикты | 34/40 (85%) | 31/40 (77,5%) |
| TP / FN / FP / TN | 15 / 6 / 0 / 19 | 13 / 8 / 1 / 18 |
| Совместно тип+время ±2с, TP / FP / FN | 9 / 11 / 13 | 8 / 10 / 14 |

Три новых ошибки: **X-4 и X-13 — TP→FN; X-14 — TN→FP (T12, 70с)**.
Сравнение использует один и тот же `data/annotations.csv`, SHA256 `c15aab36c786d9fd3111018952ce0b2cd89e51ff3b133d7441e5ea5f5904148f`.
Это не снижение из-за HTTP timeout: все 40 запросов в новом прогоне завершились `done`.

В `0112-b9a1` проверены только X-4, X-13 и X-5: два пропуска исправлены, чистый X-5 остаётся чистым. **X-14 не проверен**, остальные 37 видео отсутствуют. Это не доказательство восстановления 85%.

`e7c2dd9` вернул 2 fps и прежнюю частоту вопросов, но сохранил отложенный поиск счётной машины. Это не точная копия исходной версии. У API-прогонов нет manifest с хэшами исходников/весов/runtime; нельзя приписать отдельную ошибку конкретной оптимизации. Полный повтор нужен на одной зафиксированной версии. Скорость ускоренного `0039` нельзя выдавать за скорость восстановленной версии.

В [docs/METRICS.md](../docs/METRICS.md), раздел «Скорость и нагрузка», Даниал сообщает: пять разных видео одновременно через публичный URL, один worker, до ускорения — **3 done за 46/108/195с, X-14 и X-39 превысили 270с**. Исходный отчёт `runs/jobs/load5-public.json` остаётся локально у Даниала и в этот аудит не поступил.

Следовательно, испытанная конфигурация не прошла приёмку пяти одновременных видео. Последовательные 40/40 этого не отменяют. На Mac 16 GB два worker ранее вызвали сильный swap; увеличивать их число без замера нельзя.

## Что исправлено в API и инструменте проверки

- Один monotonic deadline на запрос: получение загрузки сервером → сохранение/ffprobe → очередь → inference → проверка результата. По умолчанию 270с; это оставляет резерв относительно 300с ТЗ, но не гарантирует задержки клиентской сети/прокси.
- Истёкший запрос до создания job получает HTTP 408 с очисткой файла и освобождением места. Операции записи не отменяются с удалением ещё используемого файла: бюджет проверяется между блоками записи и после завершения; ffprobe получает оставшееся время.
- Истёкший queued job становится `failed`, даже если worker ещё занят другой задачей. Он не запускает модель и не возвращает `no_violation`. Освобождение слота остаётся ровно одним.
- Проверка итогового JSON также входит в бюджет. После перезапуска незавершённые задания по-прежнему считаются failed; сохранённый monotonic deadline повторно не используется.
- `service.cli check`: загрузка больше не ограничена отдельными 40с; каждый запрос использует остаток общей границы 300с. `elapsed_sec` — время получения и проверки публичного результата; `verification_elapsed_sec` отдельно учитывает внутренний `/details`.
- Если `/details` не подтверждён, отчёт получает `verification_failed`, сохраняя `public_status` и время. Неполные события не передаются batch-потребителю как успешное предсказание.

Это исправляет учёт и обработку отказов, **не ускоряет модель и не улучшает accuracy**. `urllib` ограничивает ожидание сокета, а не строго обрывает непрерывно капающее тело; проверка после чтения запрещает принять такой опоздавший ответ. При зависшем диске абсолютное время также нельзя гарантировать. Финальная приёмка измеряется с внешнего клиента.

## Следующие действия без дублирования работы

1. **Даниал:** зафиксировать код/настройки, сохранить commit и source/model/runtime fingerprints; повторить весь real API-набор без кэша. Сравнить вердикты и события, обязательно X-4/X-13/X-14. Перед публикацией 85% нужен полный результат.
2. **Даниал:** на той же версии пять разных файлов одновременно, включая длинный и дорогие случаи. `service.cli check` принимает пять путей с `--count 5 --strict --expect-engine real --url <публичный URL> --report runs/jobs/load5-public.json`; ключ только в `.env.local`. Сохранить RAM/swap. Для пересылки удалить ключи/кадры/описания, оставить метаданные результата.
3. Если не укладывается — профиль загрузки моделей, RT-DETR и VLM; ускорение принимать только после сравнения качества. Постоянный worker может убрать повторную загрузку весов, но выигрыш надо измерить; такая архитектура ещё не реализована.
4. **Бигали:** финальные цифры SUBMISSION брать из полного проверенного прогона; временный URL не считать доказательством нагрузки. Закрытые собственные видео сохранить независимыми до фиксации версии.
5. **Асылбек:** тесты API, smoke на пяти разных синтетических MOV, checkpoint и сообщения с результатом. Реальные модели здесь не запускались: на Windows нет локальных весов/MLX.
