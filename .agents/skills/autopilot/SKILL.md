# Autopilot: один виток «гипотеза → прогон → вывод → push»

Ты ведёшь ML-поток сам. Один вызов = один виток (под `/loop` — следующий виток в следующем вызове). Цель витка — **проверенное** улучшение метрики из `task.toml` или честный вывод, что гипотеза не сработала. Никогда не «улучшай» скор ценой валидации.

## 0. Где мы
- `scripts/sync.sh` (подтянуть работу напарника, входящие). Строка «⏱» — сколько до фриза. После фриза (вс 08:00) новых экспериментов не начинай: только финальный сабмит лучшей модели и выход.
- Прочитай: `task.toml`, «Контракт» и MVP в `docs/REQUIREMENTS.md`, хвост `docs/EXPERIMENTS.md` (30 строк), `uv run python -m app.cli runs -n 10`, свой `docs/tasks/<id>.md`.
- Прогонов ещё нет → виток = бейзлайн: `uv run python -m app.cli auto --quick --eda --note "baseline"` (фон), затем полный `auto`.

## 1. Выбор гипотезы (одна на виток)
Возьми из «Что попробовать дальше» последнего `runs/<run_id>/report.md`, очереди в `docs/tasks/<id>.md` или своей оценки. Приоритет по **ожидаемому приросту на час работы**:
1. Ошибка постановки: не та метрика/валидация, утечка, потерянная таблица, дубли — чинить первым.
2. Данные: агрегаты таблиц событий (`app.features.aggregate_by`), джойны справочников, признаки из дат (давность, сезонность), отношения (долг/доход, загрузка лимита) — в `app/custom_features.py`.
3. Модель: `uv run python -m app.cli tune --model <лучшая> --minutes 30` (фон), веса классов для редкого класса, другой порог.
4. Ансамбль и стабильность: больше фолдов, усреднение сидов — только когда 1–3 исчерпаны.
Запиши гипотезу одной строкой в «Сейчас» своего `docs/tasks/<id>.md`: «гипотеза → ожидаю +X к метрике, потому что …».

## 2. Прогон
- Меняешь код — только в своей зоне. Сначала быстрая проверка: `uv run python -m app.cli auto --quick --note "<гипотеза>"` (3 фолда, ≤100k строк). Дало прирост → полный `auto` (в фоне, run_in_background) с той же заметкой.
- Долго (> 20 мин на ноутбуке) или нужен GPU → скилл `colab`.
- Упало → прочитай `runs/<run_id>/agent_log.jsonl` (шаги со статусом fail), почини, повтори. Дважды одна и та же ошибка → `scripts/new-skill.sh`.

## 3. Проверка результата (до того, как радоваться)
- Сравнивай с лучшим прогоном **с той же метрикой и CV** (`app.cli runs`). Прирост меньше разброса по фолдам (± в отчёте) — это шум, а не улучшение.
- Предупреждения отчёта («подозрительно высоко», «почти не лучше dummy», сдвиг train→test) — разбери каждое. Новый признак резко стал топ-1 → проверь, не знает ли он будущее (известен ли он на момент решения банка).
- Сабмит проверен оркестратором (строки, пропуски, колонки = sample_submission) — шаг `submit` должен быть ok.

## 4. Вывод и push
- Строка в `docs/EXPERIMENTS.md` дописалась сама; добавь под ней вывод одной строкой: «✔/✖ гипотеза — почему» (ручные эксперименты из ноутбука — строку целиком).
- Улучшение подтвердилось → `scripts/msg.sh all "[SCORE] <run_id> <метрика> <было → стало>: <что сработало>"`. Нашёл бизнес-закономерность → `[INSIGHT]` напарнику (он ведёт `docs/INSIGHTS.md`).
- Обнови `docs/tasks/<id>.md` («Готово» с run_id), затем `scripts/checkpoint.sh "exp: <гипотеза> → <метрика> (R-ID)"`.

## 5. Следующий виток
- Под `/loop` — закончи ход кратким итогом (гипотеза, run_id, было → стало, следующая гипотеза); следующий виток начнётся сам. Без `/loop` — предложи человеку следующую гипотезу и спроси, продолжать ли.
- Ждёшь долгий прогон или ответ напарника — не простаивай: подготовь следующую гипотезу на выборке или помоги с графиками для питча в своей зоне.
- Стоп-условия: фриз; три витка подряд без прироста → смени направление (данные вместо модели) и сообщи человеку; ошибка, которую не можешь починить за 2 попытки → `[BLOCKED]` и остановись.
