# Краткое объяснение решения (1 страница для жюри и менторов)

Состояние на 17.10, после `2207-cebf`, real API `2214-5d08` и инженерного аудита. Метрика development-набора, не финальный результат жюри.

## Задача и ценность для банка

Помочь проверяющему найти возможные нарушения кассовой дисциплины в видео: показать тип, время, кадры и нормативное основание. Человек проверяет доказательства и принимает решение. Экономию времени и денег пока не измеряли.

## Данные и валидация
40 уникальных видео после объединения дубликатов, 21 с нарушением и 19 чистых, 22 размеченных события. Правила подбирались на этом же наборе; это development-оценка. X-24 подтверждён как T11: исправленный Word v4 (`4d4c0b7`) согласован с CSV, Даниал подтвердил в 23:02. Независимая проверка нового ракурса ещё нужна.

## Решение
MOV → кадры 2 fps → Grounding DINO находит предметы → RT-DETR отслеживает людей → временные правила выделяют кандидатов → локальная Qwen3-VL проверяет обрезки → фиксированный каталог нормативных оснований → API/UI. Кадры сохраняют исходное разрешение; временный файл и ограниченный кэш снижают RAM. Внешние AI API не получают видео, кадры или описания случаев. Real пока работает на Apple Silicon/MLX.

## Результат
`runs/eval/20261017T2207-cebf`: **34/40 = 85%** вердиктов; обнаружено 15/21 нарушающих видео, FP 0/19. Совместно правильные тип и время ±2с — **9/22 событий**, без повторного использования одного предсказания. [Воспроизводимый аудит](../service/reports/quality-latest.json).

Все 40 записей `2207-cebf` имеют `vlm_calls=0`: это кэш. Отдельный [`runs/jury/20261017T2214-5d08`](../runs/jury/20261017T2214-5d08/metrics.json) содержит 40 strict real API-проверок без синтетики, 40/40 `done`, 33.934–120.211с; вердикты, типы и времена совпадают с `2207-cebf` на всех 40 видео. Это последовательные запросы, не проверка пяти одновременных. Новые инженерные изменения и шпаргалка сценариев не имеют измеренного прироста accuracy. 98% не достигнуты и не заявлены.

## Главные инсайты
1. Правильный вердикт не гарантирует правильные тип и таймкод — поэтому оцениваем совместное попадание событий.
2. Мелкие детали (ключ, документ) и стеклянная дверь остаются сложными; увеличение общего процента не заменяет проверки этих пропусков.
3. Изолированные задания и ограниченная память важны для доступности сервиса. Синтетический decode 1080p показал 371.71 → 167.42 MiB peak RSS при совпадении всех пикселей; это не память всего ML-процесса.

## Демонстрация за 60 секунд
Открыть UI, указать ключ, загрузить MOV, дождаться результата, перейти к таймкоду и кадрам, открыть нормативное основание. Для реальной демонстрации выбрать `VISION_ENGINE=real`; синтетический/mock запуск обозначать явно. Проверка интеграции: `uv run python -m service.smoke`, пять разных входов и автоматическая остановка сервера.

## Ограничения и что дальше

Открыто: T3/T6/T13, часть T7/T9, точность времён, независимый ракурс, пять одновременных real запросов <300с, публичный HTTPS. Сохранённые артефакты подтверждают последовательную real API-проверку; после изменений нужна регрессия. Два worker на Mac 16GB, по сообщению Даниала, вызвали сильный swap — сохраняем один до новых замеров. Хост не арендован, публичного URL пока нет.

[Шпаргалка новых случаев](SCENARIO_GUIDE.md) содержит 30 сценариев с условиями и контрпримерами. Это подготовка к экспериментам, не 30 работающих детекторов; неизвестные события автоматически через T0 не классифицируются.

Ближайший эксперимент — локальная проверка ручного пересчёта T9 по трём последовательным кадрам с чистыми контрпримерами; новый detector включается только после сравнения на фиксированных метках. Формат защиты: 5 минут + 2 минуты вопросов. Питч/deck готовит Искандер, факты брать из этой записки и актуальных проверенных run.
