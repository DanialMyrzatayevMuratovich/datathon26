## Пять направлений по приоритету

### 1. Зафиксировать базу и вернуть потерянный T7

- Сохранить текущий checkpoint и сравнивать каждую гипотезу с ним на **всех 40** видео, не только на исправляемых примерах. Показывать переходы TP→FN и TN→FP.
- Для X-18 / чистого X-39 проверить трек человека и пересечение зоны кассира относительно стола/двери. Присутствие стоящего человека само по себе не доказывает постороннего: этот вариант уже дал FP и отвергнут.
- Не возвращать старую геометрию целиком: сравнить отдельно `cashier_depth`, `cashier_track`, `near_cash`. Состояние «кто-то у стола» не равно «кассир на месте»: `Tracks.present` по-прежнему считает любого человека. Отдельно проверить уход кассира, когда клиент остаётся.
- Критерий принятия: X-18 восстановлен без новых FP и без потери уже найденных нарушений. Не использовать имя файла/ракурс как условие в production-коде.

### 2. T9: распознать действие и его начало, а не просто наличие денег

Сейчас T9 добавился, но его времена не попадают в событие:

| Видео | Разметка T9 | Текущий T9 |
|---|---:|---:|
| X-1 | 22 с | 1.5 с |
| X-4 (с дубликатом X-47) | 68 с | 21 с |
| X-13 | 47 с | 31.5 с |
| X-2 | 10 с | пропуск |
| X-44 | 16 с | пропуск, confidence разметки low |

- Причина в коде: таймкод берётся из `cash[0]`, это первый из нескольких кадров с наличными. Он не означает начало ручного пересчёта. Не исправлять общей константой сдвига: разница здесь неодинакова.
- Кандидат — последовательность движения рук/купюр в ROI, затем локальный эксперт на 3–4 упорядоченных кадрах: «ручной пересчёт / использование машины / перемещение или уборка пачки / неразличимо». Доступный `vlm.ask(images, ...)` уже принимает список изображений. Это **эксперимент**, качество и стоимость ещё не измерены.
- Сначала дешёвые кандидаты на 2 fps, затем уточнение начала в коротком окне более частыми кадрами. Не увеличивать fps всего ролика: это дорого и не решает смысл события.
- Отрицательный ответ «машина не работает» недостаточен: на чистых X-3/X-5/X-19/X-37 VLM также не увидела её работу. Нужен положительный признак пересчёта, а отсутствие использования машины оценивается в том же окне операции.
- Проверить отдельно cash-only вход: текущий `ctx = ... if events else []` ограничивает T9 в основном уточнением уже найденного нарушения (кроме сумки). Без нового положительного action-detector он не восстановит X-2/X-44.
- Критерий: больше совместных type+time hits, восстановленные пропуски, без новых ложных тревог. X-44 сначала проверить человеком; не менять метку только потому, что модель не совпала.

### 3. T6 и T3: сначала проверка видимости, затем правило

- **T6:** предыдущая вырезка двери давала «открыта» 21/21 даже на закрытой X-31. Повторять тот же yes/no бессмысленно. Сравнить маленькую вырезку с контекстом рамы/петель и соседней стены, а также 2–3 кадрами до/после движения двери. Проверять на X-31 против X-32/X-33 и других чистых роликов. Если состояния не различимы, честно оставить ограничение; «всегда открыто» не является детектором.
- **T3:** и 4B, и 8B уже дали 0/3, включая плотную вырезку; повторная смена размера VLM без новой информации не приоритет. Сначала человек проверяет видимость ключа на исходном разрешении. Если ключ занимает несколько пикселей, увеличение картинки не создаёт потерянную информацию.
- Узкий классификатор ключа имеет смысл только при новых независимых положительных/отрицательных примерах и разделении по исходному видео/сцене. Два известных положительных видео недостаточны для честного заявления о 98–99%.
- Ограничить такой feasibility-эксперимент 15–20 минутами. При отрицательном результате перейти к таймкодам и надёжности, а не бесконечно переформулировать вопрос.

### 4. Убрать T8 FP и проверить временную логику

- Единственный оставшийся binary FP — X-35, T8 на 54.5 с. По разбору Даниала это уборка денег, а не пересчёт. `Q_HANDLING` объединяет разные операции; упорядоченные кадры с выбором действия полезнее одиночного «есть ли работа с деньгами».
- Ветка T8 проверяет `was_client`, затем работу на e+1.5/e+4 с, но **не проверяет, что клиент оставался отсутствующим всё это окно**. Короткое выпадение детекции не должно означать уход. Проверить непрерывное отсутствие/возврат и привязку к операции без предположений о владельце денег.
- Не возвращаться к «T8 только при работающей машине»: это уже потеряло X-34/X-38.
- T4: `SAFE_OPEN_MIN_S=6` объявлена, но правило использует `len(streak)>=2` при неравномерном `when`. Это не фиксированные 6 секунд непрерывного состояния. Если длительность нужна правилу, считать её по timestamp и учитывать разрывы наблюдения; не менять порог без проверки чистых X-14/X-25.
- `has(type_id)` подавляет повторные события одного типа во всём видео. Для новых роликов с несколькими событиями нужна дедупликация по временному окну события, а не один результат на тип за весь ролик.

### 5. Воспроизводимость, кэш, независимая проверка и SLA

- `DevCache.vlm` ключуется только pixels+question, без имени/ревизии VLM. Ключи `scene`/`dets` также не включают detector revision, fps и параметры. При смене модели/препроцессинга создать отдельный namespace кэша либо пересчитать соответствующий этап. Иначе A/B может сравнивать одинаковые старые ответы. Локальный кэш может ускорять подбор **неизменённых** этапов, но не подтверждает финальную скорость.
- `vision.evaluate` без `--cache` не очищает экспортированный `DT_CACHE`. Для чистого запуска на Mac: `env -u DT_CACHE VISION_ENGINE=real uv run python -m vision.evaluate`. Два прогона одной версии, затем `--compare RUN1 RUN2`. API-worker уже принудительно отключает этот кэш.
- Уже просмотренные 40 видео не становятся независимым тестом после нового разбиения. A/B по ракурсу — полезный стресс-тест, но честный финальный контроль — новые ролики другого ракурса, не использованные при подборе. При обучении по кадрам все кадры одного видео/дубликаты остаются в одной группе. Основание: [предотвращение утечки](https://scikit-learn.org/stable/common_pitfalls.html#data-leakage), [групповые проверки](https://scikit-learn.org/stable/modules/cross_validation.html#cross-validation-iterators-for-grouped-data).
- 3–4 изображения за запрос поддерживаются интерфейсом текущей обёртки; возможности multi-image/video описаны в [официальном Qwen3-VL](https://github.com/QwenLM/Qwen3-VL). Это не доказательство качества временной классификации на наших роликах — нужны локальные проверки.
- После каждой принятой гипотезы: полный прогон, joint-метрики, latency; новые вопросы VLM должны помещаться в <300 с через API. Общий пик RAM измерять при двух worker, учитывая unified memory/swap; сумма RSS не равна точному потреблению физической памяти Apple GPU.

## Команды, которые можно брать агенту

Дополнительная проверка уже сохранённого прогона, без моделей и видео:

```bash
uv run python -m service.quality runs/eval/20261017T2123-fb5e/predictions.json --report runs/jobs/quality-check.json
```

Для нового прогона заменить путь predictions. Инструмент не меняет `vision.evaluate`, разметку, модель или официальный score. Неполное покрытие/лишние видео: exit 2, итоговая accuracy = null; один prediction не может закрыть два события. Обычный exit 0 означает валидный полный отчёт, **не** готовность модели или достижение целевого качества.

В API-приёмку добавлены несколько входных файлов и защита от случайного mock:

```bash
# Пять разных файлов: подставить реальные пути, включая самый длинный, чистый и несколько типов.
uv run python -m service.cli check a.mov b.mov c.mov d.mov e.mov --count 5 --strict --expect-engine real --report runs/jobs/real-five.json
```

Один путь с `--count 5` по-прежнему повторяет один файл пять раз. Отчёт теперь содержит индекс/имя входа, type_id/таймкод, время и engine, без кадров/описаний/ключа: его можно сопоставить с прямым прогоном модели. `--expect-engine real` проверяет health **до загрузки**, затем запрещает mock-результаты.
