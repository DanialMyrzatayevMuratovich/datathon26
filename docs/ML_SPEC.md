# ТЗ на ML-часть: распознавание нарушений кассовой дисциплины по видео

Наше внутреннее ТЗ (поток danial), отдельно от ТЗ кейса (`docs/TASK.md`). Сервис, API и интерфейс — не здесь (`docs/REQUIREMENTS.md`, потоки asylbek и bigali).

## 1. Цель
По видеофайлу выдать вердикт `violation` / `no_violation` и список возможных нарушений: тип (12 фиксированных + «иное»), таймкод, 1–3 кадра-доказательства, описание того, что видно, и норму из каталога. Качество меряем на обучающих видео и на своих роликах под другим углом.

## 2. Вход и выход (контракт, не меняется без `[CONTRACT]`)
- Вход: путь к `.mov` (≥ 29 fps, без звука, до ~145 с, ~29 МБ), колбэк прогресса.
- Выход: `vision.analyze(path, progress) -> contract.schemas.VideoAnalysis` — verdict, violations[type, type_id, timecode_sec, start/end, confidence, description, evidence_frames (JPEG base64), rules, why], duration, processing_sec, engine.
- Нормы — только из `data/laws/rules_catalog.json` (дословные цитаты); модель ссылки не генерирует.

## 4. Что распознаём
12 типов — `docs/VIOLATIONS.md` (T1–T12), запасной T0 «Иное нарушение кассовой дисциплины» (только при сильном сигнале, иначе не выдаём). Таймкод — **момент начала события** (уход, вход, передача, открытие), кадр-доказательство — из окна [t−1; t+3] с лучшей видимостью.

## 5. Целевые метрики (на 40 уникальных видео; Х-47 = Х-4, Х-48 = Х-5)
| Метрика | Цель | Почему |
|---|---|---|
| Полнота вердикта (нарушение найдено в видео с нарушением) | ≥ 0,95 | пропуск недопустим (FAQ 16) |
| Точность вердикта (нет ложной тревоги на чистом) | ≥ 0,80 | ложных — минимум |
| Верный тип среди найденных | ≥ 0,70 | 15 баллов |
| \|Δt\| ≤ 2 с от разметки | ≥ 0,80 событий | 15 баллов |
| Время 145-секундного видео | ≤ 2 мин | О5 |
| Свои ролики под другим углом: полнота | ≥ 0,80 | устойчивость, 10 баллов |

## 6. Архитектура — гибрид без обучения «с нуля»
1. **Кадры**: 2 к/с (145 с → 290 кадров), фиксированные моменты времени.
2. **Детектор** людей и предметов на каждом кадре → треки (кассир, клиенты, посторонние), предметы на столе.
3. **Разметка сцены** один раз на видео: где стол, сейф, ноутбук, дверь — от найденных объектов, а не от пикселей (устойчивость к ракурсу).
4. **Правила** превращают последовательность состояний в кандидаты событий: «кассир вышла из зоны», «в зоне кассира второй человек», «после ухода на столе предмет», «клиент ушёл, а у машины работа» и т. д.
5. **VLM-эксперт** смотрит только кадры кандидатов (обрезка и увеличение нужной области) и отвечает на точные вопросы с ответом да/нет («Ключ в замке сейфа?», «Дверца сейфа открыта?», «На экране ноутбука рабочее окно?»), пишет описание.
6. **Сборка**: тип → норма из каталога → описание («Нарушен…» / «Может противоречить…») → `VideoAnalysis`.

## 9. Протокол проверки и двойной прогон
1. **Детерминизм**: фиксированные моменты кадров, сиды, VLM с температурой 0, зафиксированные версии и ревизии весов, все пороги в одном конфиге `vision/config.py`.
2. **Прогон 1**: `uv run python -m vision.evaluate --videos data/raw/open/videos --labels data/annotations.csv` → `runs/eval/<run_id>/`: `predictions.json` (по каждому видео), `metrics.json`, `report.md` (ошибки с кадрами).
3. **Прогон 2**: та же команда ещё раз → `vision.evaluate --compare <run1> <run2>`: вердикты, типы и таймкоды должны совпасть **полностью**, тексты описаний — тоже. Любое расхождение = недетерминизм, ищем и чиним до перехода дальше.
4. **Прогон через сервис**: те же 5 видео через API Асылбека → сравнение с прогоном 1 (результат API = результат пайплайна).
5. **Разметка тоже проверяется**: люди пересматривают Х-1, Х-24, Х-44, Х-13, Х-17; правки — в `data/annotations.csv` отдельным коммитом, метрики пересчитываются.
6. Итог каждого значимого прогона — строка в `docs/METRICS.md` (run_id, что меняли, метрики §5, время).

## 12. RAG — доступ системы к законам и к нашим разборам видео
Всё локально: эмбеддинги считаются моделями из §7, индекс — `numpy` + JSON в `data/rag/` (несколько МБ, входит в Docker-образ), сервер не нужен.

| Индекс | Что внутри | Модель | Зачем |
|---|---|---|---|
| **Законы** | пункты правил НБРК № 231, № 14 и Требований АРРФР № 53 (главные) + Закон о банках, КоАП, НП ВС о трудовых спорах (`data/laws/`) | bge-m3 | норма для **нового типа** (T0, которого нет в каталоге); «смежные нормы» в интерфейсе |
| **Разборы видео (текст)** | определения 12 типов (`docs/VIOLATIONS.md`), 22 описания нарушений и 20 чистых сценариев (`data/annotations.csv`) | bge-m3 | сопоставить описание от VLM с ближайшим типом — названия типов всегда из фиксированного списка |
| **Разборы видео (кадры)** | кадры-доказательства размеченных нарушений и кадры чистых роликов (обрезки областей: стол, сейф, ноутбук, дверь) | SigLIP2 | найти **похожий размеченный случай** и дать его VLM как пример («так выглядит ключ, оставленный в замке») |

**Правила безопасности RAG (критерий 4 — штраф за выдуманные ссылки):**
1. Для 12 известных типов норма берётся **только из каталога** `rules_catalog.json`; RAG по законам — лишь для T0.
2. VLM выбирает норму **из найденных кандидатов по ID** (ответ JSON), текст цитаты подставляет код дословно из корпуса — модель не пишет ссылки сама.
3. Порог сходства: ниже — «норма не определена, требуется проверка», выдумки нет. Такие нормы всегда помечаются как трактовка.
4. **Без утечки при оценке:** когда проверяем видео X, его кадры и описание (и его дубликат) исключаются из индекса разборов — иначе метрики завышены.
