# Ship: сдача, которую нельзя завалить

## Текущий видео-кейс ForteBank

Для `docs/TASK.md` с MOV/API выполнить эту ветку вместо табличной ниже:

1. Зафиксировать проверенный commit, модель и разметку. Два чистых real runs с manifest, полным coverage и успешным `vision.evaluate --compare RUN1 RUN2`; записать binary recall/FP и joint type+time. Разрешить спорные метки с человеком; новые ракурсы не подмешивать в tuning до проверки.
2. `scripts/smoke.sh --local` проверяет свежий checkout на пяти разных синтетических MOV (mock). `scripts/smoke.sh --local --with-data` — локальную полную оценку и пять разных real API-входов, включая самый длинный. Данные не копируются в Git/AI-review. Для второго нужны Mac и локальные веса; mock smoke не закрывает real SLA.
3. Публичный HTTPS: `service.cli check ... --count 5 --strict --expect-engine real --url https://HOST --report runs/jobs/public.json`. Ключ только в локальном окружении. Проверить UI с другого устройства, время каждого запроса <300с, сохранение результатов после рестарта. Хост/оплату не считать созданными без фактической приёмки и разрешения владельца.
4. Согласовать README, JURY_BRIEF, SUBMISSION и питч по одним run_id/меткам. Формат питча 5+2 минуты. Каждый незакрытый R-ID оставить видимым; 85% на development-наборе не превращать в независимую accuracy.
5. `scripts/judge.sh` создаёт только пакет документации и агрегатов. AI-критик читает только этот пакет; никакого raw/video/frames/predictions/cache и свободного доступа к локальному датасету. Локальный smoke выполняется отдельно от внешнего AI-review.
6. Записать реально выполненные проверки в `docs/TESTING.md`; PDF/резервную копию и ссылку/ключ для сдачи передать человеку. Checkpoint до вс 11:30, остановиться по расписанию. Старый табличный CSV submission для этого кейса не создавать.

## Вспомогательная сдача другого, табличного кейса

Жюри (или его модель) открывает репо, читает README и сверяет цифры питча с кодом. Не воспроизводится — минус доверие ко всему остальному.

1. **Финальная модель**: `uv run python -m app.cli runs` → лучший прогон по метрике ТЗ с честной валидацией (не самый высокий скор с предупреждением «подозрительно высоко»). Его сабмит — `outputs/submissions/<run_id>.csv`; при необходимости загрузи на платформу организаторов и сохрани скриншот/ответ в `docs/TESTING.md`. `models/best.json` указывает на него.
2. **README** — на русском, по шаблону файла, разделы не переставляй: название и одна фраза; задача и как мы её поняли; результат (метрика vs бейзлайн и dummy, схема валидации); главные инсайты (ссылка на `docs/INSIGHTS.md`); как работает решение (от данных до сабмита, mermaid-схема); технологии; установка и запуск (≤ 3 команды, `uv sync` → данные в `data/raw/` → `app.cli auto`); как проверить (копируемые команды: вход → ожидаемый выход и где он лежит); данные (откуда, что не в git и почему); ограничения; команда; как мы работали с AI-агентами; заранее подготовленное (`docs/PREPARED.md`). Пиши только то, что подтверждается репо. Удали все подсказки `<!-- -->`.
3. **Трассировка**: таблица R-ID → что сделано → файл/команда → как проверить → статус (✅ / ⚠️ / ❌). Не сделано — так и пиши.
4. `scripts/checkpoint.sh "docs: README for submission"` → `scripts/smoke.sh --with-data` (свежий clone + реальные данные → та же метрика) и `scripts/smoke.sh` (без данных, на демо). Любой FAIL чинится первым.
5. `scripts/judge.sh` (в фоне, 3–8 мин) → сделай из его топ-5 исправлений те, что влезают до 11:30; его «неудобные вопросы» → в Q&A `docs/PITCH.md`.
6. **`docs/TESTING.md`** — журнал проверок: автотесты, smoke, проверка судьи и что исправили, ручные проверки демо, известные ограничения. Только то, что реально выполнено.
7. **Проверь каждое утверждение** README, `docs/INSIGHTS.md`, `docs/PITCH.md`, `pitch/deck.md` — команды, пути, цифры, run_id: выполни или открой — и выведи таблицу «утверждение → как проверено → ✅/❌». Каждое ❌ исправь или убери.
8. Экспорт презентации в `pitch/deck.pdf` (скилл `pitch`, шаг 6) и копия на флешку/в Drive — на случай отказа ноутбука.
